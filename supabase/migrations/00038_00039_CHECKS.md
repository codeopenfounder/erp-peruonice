# Verificación de las migraciones 00038 y 00039

No son migraciones: son las consultas para comprobar el estado antes y después.
Ejecutar en el SQL editor de Supabase.

## Antes de aplicar

```sql
-- 1. Cajas activas y qué series tiene cada una.
--    Esperado hoy: CAJA-01 con B001 y F001; CAJA-02 con NINGUNA.
SELECT cr.code, cr.name, cr.is_active,
       coalesce(string_agg(s.series_code || ':' || s.document_type, ', ' ORDER BY s.series_code), '(sin series)') AS series
FROM cash_registers cr
LEFT JOIN invoice_series s ON s.cash_register_id = cr.id AND s.is_active
GROUP BY cr.id, cr.code, cr.name, cr.is_active
ORDER BY cr.code;

-- 2. branch_id de las series. Esperado hoy: todas en NULL.
SELECT series_code, document_type, branch_id, cash_register_id, current_correlative
FROM invoice_series ORDER BY series_code;

-- 3. Que no exista ya un B002/F002 atado a otra caja (chocaría con el
--    UNIQUE (tenant_id, series_code)).
SELECT series_code, cash_register_id FROM invoice_series
WHERE series_code IN ('B002', 'F002');

-- 4. Que ninguna caja tenga hoy DOS series activas del mismo tipo: si las
--    tuviera, el índice único parcial de 00038 fallaría al crearse.
SELECT tenant_id, document_type, cash_register_id, count(*)
FROM invoice_series
WHERE cash_register_id IS NOT NULL AND is_active
GROUP BY 1, 2, 3 HAVING count(*) > 1;
```

Si la consulta 4 devuelve filas, hay que desactivar las sobrantes **antes** de
aplicar 00038, decidiendo cuál se queda (la que tenga el correlativo más alto).

## Después de aplicar

```sql
-- 1. Cada caja activa con serie de boleta y de factura propias.
--    Esperado: CAJA-01 -> B001/F001, CAJA-02 -> B002/F002.
SELECT cr.code, s.series_code, s.document_type, s.current_correlative, s.branch_id
FROM cash_registers cr
JOIN invoice_series s ON s.cash_register_id = cr.id AND s.is_active
WHERE cr.is_active
ORDER BY cr.code, s.series_code;

-- 2. branch_id relleno y coincidiendo con el de su caja. Esperado: 0 filas.
SELECT s.series_code, s.branch_id, cr.branch_id AS branch_de_la_caja
FROM invoice_series s
JOIN cash_registers cr ON cr.id = s.cash_register_id
WHERE s.branch_id IS DISTINCT FROM cr.branch_id;

-- 3. Las series de notas siguen compartidas (caja NULL) a propósito.
SELECT series_code, document_type, cash_register_id
FROM invoice_series WHERE document_type LIKE 'nota%' ORDER BY series_code;

-- 4. El índice único parcial existe.
SELECT indexname FROM pg_indexes
WHERE indexname = 'idx_invoice_series_register_type_active';

-- 5. Correlativo de resumen: dos llamadas seguidas devuelven 1 y 2.
--    OJO: consume correlativos reales. Usar una fecha imposible y borrar después.
SELECT public.fn_next_summary_correlative(
  (SELECT id FROM tenants LIMIT 1), 'RA', DATE '1999-01-01');
SELECT public.fn_next_summary_correlative(
  (SELECT id FROM tenants LIMIT 1), 'RA', DATE '1999-01-01');
DELETE FROM sunat_summary_counters WHERE reference_date = DATE '1999-01-01';

-- 6. Tablas y RLS de 00039.
SELECT tablename, rowsecurity FROM pg_tables
WHERE tablename IN ('sunat_summaries', 'sunat_summary_counters');
```

## Qué NO hace ninguna de las dos

- No toca `invoices` ni sus correlativos históricos. Los huecos de `B001` se
  quedan como están: SUNAT valida unicidad, no continuidad, y reutilizar un
  número ya enviado sí produce rechazo (0402).
- No reinicia ningún contador existente.
- No cambia `fact_config.provider`.
